- **Calls: reconnect instead of dropping (ICE restart + wake lock)**: reported as "kabhi kabhi call per join ho jaate hain but jyada der nahi hote". Three things were killing calls that would otherwise have survived, plus one that killed them silently.
  1. `onconnectionstatechange` ran `endCall()` the instant `connectionState` became `failed`, and gave `disconnected` only an **8 second** grace. On mobile, a WiFi↔cellular handoff, a signal dip, or a free TURN relay hiccup routinely produces `disconnected` for far longer than that, so perfectly good calls were being hung up. `disconnected` now gets `CALL_DISC_GRACE` (30s) and `failed` no longer ends the call at all — both go through `handleCallDrop()`, which performs an **ICE restart** first and only calls `endCall()` if that fails. `closed` still ends immediately (nothing to restart).
  2. There was **no restart mechanism of any kind**. New `sendIceRestartOffer()` / `applyRenegOffer()` do a standard renegotiation on the *same* `RTCPeerConnection` (`createOffer({ iceRestart: true })`), so the `MediaStream`s and the call UI are untouched — only the network routes are re-found. Exchange happens over three new call-doc fields (`reneg_offer`, `reneg_answer`, `reneg_req`) rather than reusing `offer`/`answer`, because `applyAnswer()` guards on `currentRemoteDescription` and would have silently ignored a second answer. Each side compares against its own `appliedReneg*` / `handledRenegReq` so a snapshot is never applied twice. Bounded by `CALL_MAX_RESTARTS` (3) with a `CALL_RESTART_GAP` (8s) cooldown, and a successful reconnect needs to land within `CALL_RESTART_WAIT` (20s) or the call ends. Only the caller may send an offer (avoids glare), so when the **callee**'s side fails it writes `reneg_req` and the caller performs the restart. New ICE candidates from the restart keep flowing into the existing `ice_from`/`ice_to` arrays, which the existing count-based loop already picks up.
  3. A connect watchdog (`CALL_CONNECT_TIMEOUT`, 35s) was added at the end of `setupPeerConn()`: a call that never reaches `connected` used to sit on screen looking alive forever (the caller's `missedTimeout` only covered the ringing phase). It now goes through the same restart-then-end path.
  4. **Screen wake lock** (`acquireCallWakeLock()` / `releaseCallWakeLock()`, `navigator.wakeLock.request('screen')`). On mobile, screen-off makes the OS throttle the page and the connection flips to `disconnected` — the single most common real-world cause of "call jud toh jaati hai par jyada der nahi". Acquired in `showActiveCallUI()` and on `connected`, re-acquired in the `visibilitychange` handler when the tab becomes visible again (the browser drops the lock on hide), released in `cleanupCall()` and `resetCallRestartState()`. All call-restart state is reset in `startCall()`, `showIncomingCall()`, `acceptCall()` and `cleanupCall()`. UI feedback: a "Reconnecting…" `showCallToast()` on `disconnected` and before every restart attempt.
- **Calls: never leave a half-set-up call behind** — reported as "caller ki calling ek second me auto cut ho jaati hai, callee ko request aati hai par accept karne par uske paas kuch nahi hota". Three independent paths produced exactly that, and all three were silent.
  1. `startCall()` wrote the call doc (`status: 'ringing'`, `offer: ''`) **before** the three awaits that build and store the offer. If `createOffer()` / `setLocalDescription()` / the `update()` failed, the `catch` only ran `cleanupCall()` — so the **caller's screen vanished within a second while the doc was left ringing forever**. The callee then rang indefinitely, and tapping Accept found an empty `offer`, burned the 20×250 ms wait loop and threw into the generic catch, i.e. nothing on their screen either. The `catch` now writes `status: 'ended'` before cleaning up, so the callee's popup closes and the call can no longer be accepted into a void. The listener is deliberately still attached *after* `setLocalDescription`: attaching it earlier would let a very fast answer arrive while `callPeerConn` is still null, and `applyAnswer()`'s `!callPeerConn` guard would drop it for good.
  2. `acceptCall()` removed `#incomingCall` and stopped the ringtone **before** `getUserMedia`. When the mic/camera permission was denied (or the context was insecure, or the mic was held by another app) it wrote `declined`, nulled `currentCallData` and returned — leaving the callee on a **completely blank screen**: no popup, no active-call UI, no message. The caller meanwhile saw their calling screen disappear because of that `declined`. It now fetches the stream first and only tears the ring UI down once it has it, and the failure path calls `cleanupCall()` and explains itself. Two more silent returns got the same treatment: the bare `if (!currentCallData) return` at the top (now dismisses the popup and toasts "Call already ended"), and the empty-offer path, which used to `throw` into a generic catch and now declines explicitly with "the caller may have hung up".
  3. **A stale `currentCallData` used to auto-decline every incoming call forever.** If a previous call never cleaned up on this device — typically a backgrounded tab whose Firestore listener was frozen and so never saw `ended` — `currentCallData` survived, and both `listenForIncomingCalls()` and `showIncomingCall()` unconditionally declined the next call behind a bare `.catch(() => {})`. That is the "kabhi kabhi" part of the report: it only bites after a previous call ended badly. New `isCallStateStale()` returns true when there is a `currentCallData` but **no** `callPeerConn` and none of `#incomingCall` / `#outgoingCall` / `#activeCall` carries `.show` — state without a UI, which can only be leftovers. Both call sites now clean up such state and take the new call; a genuinely busy user (live UI or live peer connection) still gets the polite auto-decline.
  4. No silent hang-ups remain: `listenCallUpdates()` shows "Call declined" / "No answer" on the caller's screen instead of the popup just vanishing, and `applyAnswer()`'s catch — previously a bare `console.error` that left a zombie call with a call UI and no media — now toasts "Could not connect the call" and routes into `handleCallDrop()` so a reconnect is attempted first.
- **Call screen: card is now 85% x 80% of the viewport** (was a 420px-wide strip). `.active-container` went from `width: min(420px, calc(100vw - 28px)); height: auto` to `width: 85%; height: 80%` plus `max-width: 100%` — percentages resolve against `.call-overlay`, which is `position: fixed; inset: 0` with a definite size, so 85%/80% map straight onto the viewport. Growing the card alone was not enough: `.remote-wrap` had a fixed `height: min(56vh, 400px)` with `flex-shrink: 0`, so the video would have stayed a short strip floating at the top of a mostly-empty card. It is now `flex: 1 1 auto` so it absorbs whatever height the controls leave over. The `@media (max-width: 768px)` block was overriding both rules with the old values (`width: calc(100vw - 20px)` and `height: min(52vh, 340px)`), so it had to be updated too or the phone — the main target — would have kept the old size. Nothing else in the call UI (avatar, self-preview bubble, control buttons) was rescaled, since that was not asked for.

## Key Decisions
- Used `sql.js` (pure JS SQLite) instead of `better-sqlite3` because Windows lacks Visual Studio build tools
- Used `prepare()`/`step()`/`getAsObject()` in voices.js instead of `database.exec()` for reliable data retrieval
- Voice page uses bottom-sheet pattern (not full page) for recording/preview states
- Recording indicator uses Firestore `recording/{convId}` collection with `onSnapshot` listener
- `setRecordingStatus(true/false)` called on start/stop/cancel of voice recording
- Pagination attempt (`limitToLast` + `onSnapshot`) removed — causes Firestore listener issues with new messages
- "NEW" badge changed from time-based (24h) to play-status-based (localStorage `listenedVoices` array)
- File split approach: SPA with CSS/JS split (not 3 separate HTML pages)

## Critical Context
- `listenMessages()` uses simple `orderBy('created_at', 'asc')` with no limit — all messages load but chat works reliably
- `loadedMsgIds` Set prevents duplicate rendering
- Voice recordings NEW badge uses `localStorage` key `listenedVoices` (array of recording IDs)
- Mobile layout fixes applied globally
- HTTP API base: `VOICE_API` variable points to backend
